## How the user likes to work
- **Less approval friction:** ask about big decisions and open design questions, not every detail.
- **Playtesting in batches:** the user plays, then sends a list of bugs and ideas. Handle a batch together, then one commit for it.
- **Commits** (the user's call, 2026-09-29: separate commits and repeated commit questions were unneeded overhead; this is the one place the rule lives):
  - One commit per task with everything that's changed in the working tree, including the user's own edits from other sessions. **Don't ask** whether to split or include; just say in one line what went in.
  - The only exceptions: leave out secrets or private material (see the privacy rule in `CLAUDE.md`), and anything you can't explain, such as asset files that changed on their own. Mention those and leave them unstaged.
  - Remind the user to save the project (Ctrl+S) before committing: git only sees what's on disk. Tests are sometimes run after a commit; a fix then goes in on top.
- **Speed:** the user often plays at ×10–×20 through the dev panel (editor only); starting, loading or deleting a game resets the speed to what that game earned, so set it again (decisions log, 2026-09-27).
- **Unneeded files** (the user's rule, 2026-09-29):
  - Delete them yourself when that's safe (unusable, or easy to get again).
  - If they might be wanted later, move them, with their `.meta`, into `/Remove Me/` at the project root instead. That folder is git-ignored and outside `Assets/`. The user backs it up outside the project and empties it.
  - Say which you did.
- **Balancing** is done by the user in the Balance Sheet; point them to the right row and column rather than changing numbers for them.
